一个基于 **FastAPI + FlagEmbedding(BGE-M3)** 的向量服务。模型在进程内**常驻内存**，通过 **HTTP/JSON** 提供批量文本向量化，内置**微批合并**与**简易 LRU 缓存**。

------

## 基本信息

- **Base URL**：`http://<host>:8000/`
- **Content-Type**：`application/json; charset=utf-8`
- **认证**：默认**无鉴权**（建议在网关/Nginx 层加 Token/签名）
- **模型**：`BAAI/bge-m3`
- **向量维度**：`1024`
- **数据类型**：`float32`（JSON 中为浮点数列表）
- **相似度建议**：若用余弦相似度，推荐设置 `normalize=true`（默认即开启）

------

## 启动与配置

### 环境变量（可选）

| 变量名           | 默认值                                      | 说明                                           |
| ---------------- | ------------------------------------------- | ---------------------------------------------- |
| `BGE_MODEL_PATH` | `/home/wmy/workspace/model_zoo/BAAI/bge-m3` | 模型路径或 HF 模型名                           |
| `BGE_USE_FP16`   | `true`                                      | 设为 `true` 在支持的 GPU 上使用 FP16           |
| `BGE_MAX_LENGTH` | `4096`                                      | 编码时默认 `max_length`                        |
| `MAX_BATCH_SIZE` | `64`                                        | **微批**最大合批条数                           |
| `MAX_WAIT_MS`    | `8`                                         | 微批最大聚合等待（毫秒）                       |
| `WORKER_THREADS` | `1`                                         | 后台 Worker 线程数（通常=1，每进程绑一张 GPU） |

### 运行

```bash
export CUDA_VISIBLE_DEVICES=0
python embed_server.py  # 监听 0.0.0.0:8000
```

多卡或多实例：每个进程绑定一张卡，前置负载均衡（Nginx/K8s）。

## 端点

### 1) 健康检查

**GET** `/healthz`

- **请求体**：无
- **响应示例**

```json
{
  "status": "ok",
  "model": "BGE-M3",
  "dim": 1024
}
```

- **状态码**：`200`

------

### 2) 向量化

**POST** `/embed`

- **请求体（JSON）**

| 字段         | 类型       | 必填 | 说明                          |
| ------------ | ---------- | ---- | ----------------------------- |
| `texts`      | `string[]` | ✅    | 文本数组，不能为空            |
| `normalize`  | `boolean`  | ❌    | 是否做 L2 归一化，默认 `true` |
| `max_length` | `integer`  | ❌    | 覆盖默认 `BGE_MAX_LENGTH`     |

**注意（微批归一化语义）**：服务端采用微批调度。当**同一微批中任意任务**要求 `normalize=true` 时，**该批次全部结果都会被归一化**。为避免歧义，生产中建议统一使用 `normalize=true`。

- **响应体（JSON）**

| 字段         | 类型         | 说明                                                         |
| ------------ | ------------ | ------------------------------------------------------------ |
| `embeddings` | `number[][]` | 与输入 `texts` 对齐的二维数组，每行是 1024 维向量            |
| `dim`        | `integer`    | 向量维度（恒为 1024）                                        |
| `elapsed_ms` | `integer`    | **服务端处理耗时（毫秒）**：从进入路由到返回，包括入队/等待/推理/序列化等整体耗时 |

- **状态码**

- - `200` 成功（若入队超时/异常，当前实现会返回 `embeddings=[]`）
  - `422` 参数校验失败（FastAPI 自动返回）
  - `5xx` 框架级异常

- **示例**

cURL：

```bash
curl -s http://127.0.0.1:8000/embed \
  -H "Content-Type: application/json" \
  -d '{
        "texts": ["集美大学校歌", "新生报到流程"],
        "normalize": true,
        "max_length": 512
      }'
```

Python（requests）：

```python
import requests
resp = requests.post(
    "http://127.0.0.1:8000/embed",
    json={"texts":["集美大学校歌","新生报到流程"], "normalize": True, "max_length": 512},
    timeout=30
)
resp.raise_for_status()
data = resp.json()
print(data["dim"], len(data["embeddings"]))
```

## 性能与行为说明

- **微批合并**：请求进入队列后，Worker 在 `MAX_WAIT_MS` 内尝试聚合到 `MAX_BATCH_SIZE`，一次前向统一处理，提高吞吐。
- **归一化**：

- - **单条请求**：是否归一化完全由 `normalize` 决定。
  - **微批请求**：如上所述，批内任意请求 `normalize=true` 将导致**整批归一化**。

- **缓存**：仅对**单文本**请求启用本地 LRU 缓存（键包含 `text`、`max_length`、`normalize`）。批量请求不缓存。
- **超时与空结果**：当前实现中，若队列等待超时或发生异常，可能返回 `{"embeddings": []}` 且状态码仍为 `200`。调用方应检查返回的向量数量是否与输入一致，并结合 `elapsed_ms` 与客户端端到端时间判断异常。
- **并发**：默认单 Worker（`WORKER_THREADS=1`）。需要更高并发/吞吐时，推荐**多进程多实例** + 负载均衡，而不是单进程多线程（以避免 GPU 竞争与上下文切换开销）。

------

## 与向量数据库的对接建议

- **Milvus**：字段类型 `FLOAT_VECTOR(1024)`；若使用 **COSINE**，建议入库向量已归一化（本服务 `normalize=true`）。
- **检索一致性**：**入库与查询**均使用相同的编码配置（`max_length`、是否归一化），避免分布漂移。

## 错误与返回码（补充约定）

| 场景                      | 返回                         | 建议处理                                 |
| ------------------------- | ---------------------------- | ---------------------------------------- |
| 参数缺失/类型错误         | `422` + 错误详情             | 修正请求                                 |
| 队列阻塞/超时（当前实现） | `200` + `embeddings=[]`      | 重试、监控 QPS、调大 `MAX_WAIT_MS`、扩容 |
| 内部异常（罕见）          | 可能 `5xx` 或 `200` + 空结果 | 记录日志并告警，排查 Worker              |

## 最佳实践

1. **统一归一化**：生产中统一 `normalize=true`，减少微批语义差异带来的困惑。
2. **批量优先**：能批量就批量，提升吞吐；小请求可以通过客户端缓冲/合批后再发送。
3. **观测**：在网关/调用端记录端到端耗时，并上报 `elapsed_ms` 差值用于定位排队/网络瓶颈。
4. **扩缩容**：通过多进程/多实例横向扩展；每实例绑一张 GPU；`MAX_WAIT_MS` 在 8–20ms 区间视场景调参。
5. **鉴权与限流**：在 API 网关层加 Token/签名、QPS 限流与熔断，保护后端。
